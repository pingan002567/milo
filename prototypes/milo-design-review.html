Milo：Agent 应用商店 + AI 组织指挥台

下载（招募）或生成调教好的 Agent 成员，组建 AI 组织，编辑组织架构，统一指挥干活。核心抽象：一个 DeerFlow 实例 = 一个成员；实例内部的 agent/subagent 编排不属于本产品范围。

01

调研结论与生态空位

字节已做好三件事：运行时（DeerFlow 2.0）、调教工具（llm-space）、包格式雏形（SKILL.md）。生态缺口恰好是本产品的两层价值：分发层与实例间编排层。

→
运行DeerFlow 2.0
单实例 SuperAgent harness
→
实例间编排：空白Milo 秘书长
组织 · 路由 · 汇报
虚线框 = 生态空位，即 Milo 的产品位置

三个决定性事实

  • DeerFlow 代际断裂：2.0（2026-06）与 1.x 不共享任何代码；1.x 的 agent 硬编码在源码三处、不可分发。产品全部基于 2.0。
  • llm-space 不是市场：是本地优先的 agent 调试/评估桌面 IDE（Thread JSON + Rubric 评分），没有任何分享机制。Milo 不与它竞争，而是消费其产出——把评测集变成市场上的"质检报告"。
  • DeerFlow 2.0 无跨实例协同：子 agent 只在实例内动态生成，实例之间没有组织概念。
证据：deer-flow Star 77k / 一个版本合并 180 PR；llm-space v4.x、仅 macOS、闭环开发；均经源码/文档逐项核实。

护城河（对比 prompt/GPTs 市场）

  • 带质检报告的 Agent：每个包附 llm-space 评测集，上架时平台复跑打分，下载前"验货"——市面上没有客观质量信号的先例。
  • 不止单体：下载 3 个 agent 得到的是能协同的组织，不是 3 个聊天窗口。
  • 生态红利：复用 DeerFlow 的 IM 渠道网关，组织可直接进飞书/微信群接单。

通用组织定位（不限于企业）

核心抽象是组织而非公司——任何需要多个 AI 成员分工协作的场景都适用，差异全部体现在组织模板层，org.yaml schema 不为场景分叉。

隐喻链条

硬护栏（不随配置开放）

  • 部门嵌套深度 ≤ 2；每层扇出 ≤ 5（监督幅度证据，见 06 节）
  • 成员之间不存在直接通信通道——一切经 秘书长 路由 + artifact 交接
意外印证：DeerFlow 已内置实例内静态编制（subagents.custom_agents + agents 目录 SOUL.md），说明"实例内"这层官方自己在做——Milo 只需发明实例间的组织与路由。
04

MiloPack：Agent 交付单元

在官方 SKILL.md 之上做"聚合 + 元数据 + 质检"，不发明新运行时概念——DeerFlow 升级时兼容成本最低。

my-legal-agent.milopack/
├── manifest.yaml            # 身份 · capabilities · 模型档位 · 权限 · 评测门槛
├── persona/system.md        # 主人设（→ 映射到 DeerFlow SOUL.md）
├── skills/…/SKILL.md        # 官方技能包原样透传
├── mcp/servers.yaml         # MCP 依赖声明
├── evals/*.thread.json      # llm-space 评测集 = 质检报告（含 rubric）
└── assets/                  # 图标 · README · 示例
capabilities
A2A AgentCard 式结构 {id, description, tags, examples}——秘书长 路由的依据
model_requirements
声明档位（basic/reasoning/vision/code）而非具体模型；部署端用 model_bindings 绑定自己的模型与密钥
permissions
双重职责：安全边界 + 升级策略判定依据——作者权限声明越收敛，用户越少被打扰
eval.min_score
平台复跑低于门槛不予上架
安全红线

包内零可执行代码（工具只引用不内嵌实现）；上架三重审查：官方 SkillScan + prompt 注入检测 + permissions 静态审查；包签名。反面证据：AutoGen 曾把 source_code 放进配置 → 任意代码执行 → 被官方弃用。

汇报关系与指挥体系

结论：层级汇报应该做，且是行业绝对共识——但价值有条件，汇报关系必须靠框架硬约束实现，不能靠 prompt 演戏。

用户唯一对话对象：秘书长
秘书长 前台结构化任务信封：objective / 输出格式 / 边界 / 预算
法务部封装为虚拟成员
内部对上不可见
财务成员
研究成员
默认并行度 ≤ 5 · 产物写对象存储，向上只传引用 + 摘要（切断 telephone game）· 不做 supervisor-of-supervisors

汇报协议

机制设计依据
双通道阻塞事项即时单条推送（明确"需要你决定什么"）；进度批量拉取，绝不弹窗中断恢复平均 23 分钟（Mark, CHI'08）
三槽位状态固定格式：在做什么 / 为什么 / 置信度与风险SAT 透明度模型：提升信任校准且不增负荷
升级稀缺化可逆性 × 外部影响 × 置信度 × 成本四维判定；override 率为健康指标CDSS 弹窗 90% 被 override 的反面教材
计划前置授权长任务先出可编辑计划，批准即授权到里程碑；偏离必须重新上报Devin / Magentic-UI 模式
拓扑自适应可并行任务并行派单；强串行任务单成员承接 + 其余只读支援串行任务上多 agent 劣化 39–70%（Google）
量化证据：中心化协调在可并行任务 +80~90%，错误放大 17.2× → 4.4×；纯树形拓扑在 MultiAgentBench 垫底；监督幅度三条独立证据链（无人机 2–4 · Graicunas 5–6 · 业界实践 3–5）收敛于 ≤5。反面教材：CrewAI 给 LLM 一个 manager 人设 → 不委派、抢活干、随语言漂移（Issues #4783/#1057）。
07

org.yaml：可编辑的编制文件

用户可以编辑组织架构——但开放的是策略编辑而非自由连汇报线。三档：L1 自动（默认，无需编辑）→ L2 声明式（org.yaml + 表单）→ L3 封装式层级（部门）。

apiVersion: milo.dev/v1alpha1        # 毕业制 v1alpha1 → v1beta1 → v1
kind: Organization
metadata: {name: due-diligence-inc, version: 1.3.0}
spec:
  members:
    - name: market-researcher
      pack: registry.milo.dev/market-researcher@sha256:ab12…   # 强制版本 pin
      runtime: {mode: container, model_bindings: {reasoning: deepseek-r1}}
  departments:
    - name: legal
      uses: registry.milo.dev/teams/legal-review@1.2.0          # 成建制引用
      inputs:  [{name: contract_files, type: artifact, required: true}]
      outputs: [{name: review_report, type: artifact}]
  routing:
    rules:                                                      # 有序匹配，CEL 求值
      - {match: 'task.capability in ["contract-review"]', assign: legal}
    default: ask_user                                           # 必填兜底
  pipelines:
    - name: full-dd-report
      tasks:
        - {name: collect, assign: research}
        - name: legal-review
          assign: legal
          depends: "collect.Succeeded"                          # Argo 式状态谓词
          inputs: {contract_files: "${tasks.collect.outputs.artifacts.contracts}"}
  escalation:
    policies:
      - {name: external-side-effect, when: 'action.permissions.network_external', actions: [block]}
      - {name: low-confidence, when: 'report.confidence < 0.6', actions: [escalate]}
      - {name: budget-80pct, when: 'usage.tokens > task.budget.tokens * 0.8', actions: [warn]}
  limits: {maxParallelMembers: 5, maxDepartmentDepth: 2, pendingQueueBackpressure: 3}
status:                                                        # 仅 秘书长 可写
  observedGeneration: 3
  members: [{name: legal, conditions: [{type: Ready, status: "True"}]}]

规范落实的十条铁律（来自 DSL 先例调研）

#铁律正 / 反面来源
1配置零可执行代码反面：AutoGen FunctionTool source_code 被弃用
2表达式语言全 DSL 只用一门：CEL正面：K8s KEP-3488；反面：Argo 三套语法并存
3结构化值层面求值，禁文本拼接反面：Argo 炸引号、GHA 表达式注入
4长 prompt 放 Markdown 正文不放 YAML 字段正面：Claude Code frontmatter+正文
5产物双通道：parameters + artifacts，大件强制引用正面：Argo；反面：ASL 256KB 限制
6封装接口类型化 + 引用强制版本 pin正面：GHA reusable workflow；反面：Argo 无 pin
7部门与成员同构递归正面：AutoGen ComponentModel
8spec/status 分离 + 控制器调和正面：K8s CRD/Operator
9策略正交双维度（failurePolicy vs actions），支持 warn 灰度正面：K8s ValidatingAdmissionPolicy
10版本毕业制 + 无损往返 + 导入兼容分级正面：K8s 废弃政策 + Dify DSL
路由的关键取舍

LLM 只做任务分解（产出带 capability 的任务信封）；信封 → 成员的匹配是确定性 CEL 求值。语义理解与路由执行分离——规避 Coze"跳转边画在图上、实际靠 LLM 猜"的不可调试性。

08

Member Contract：六动作与 DeerFlow 落点

Milo 与成员之间的唯一接口。适配层双实现：容器成员（HTTP Gateway，生产）/ 进程内成员（DeerFlowClient 嵌入，本地与 MVP）。

动作语义容器成员落点（源码核实）
enroll加入起容器 → MiloPack 渲染 config.yaml → POST /api/agents（persona → SOUL.md）→ PUT /api/skills/custom/{name} → /api/mcp/config
assign派单POST /api/threads → goal → POST …/runs/stream（assistant_id 选 persona · webhook 回调 · multitask_strategy: reject）
status三槽位汇报SSE 消费；断线 GET …/runs/{id}/stream + Last-Event-ID 续传；适配层归一化
escalate决策上抛澄清/中断类事件 + 终止原因 → 归一化为 input-required。事件形态 = spike 首要验证项
deliver交付webhook → workspace-changes 变更清单 → GET …/artifacts/mnt/user-data/outputs/… → 按 output_spec 校验
dismiss退出归档 thread → 销毁容器

任务状态机（借 A2A 裁剪，终态不复活）

queued→ assigned→ working⇄ input-required（escalate）→ delivered→ accepted
任一活跃态 ↘ failed canceled rejected — 后续工作创建新任务，以 context_id 关联、parent_task 回指
打扰路径同样遵守层级：subagent 的问题先汇聚到实例 Lead，再以成员身份 escalate；Milo 不接收 subagent 级信号

任务信封（结构化委派四要素为 schema 强制）

{ "task_id": "t-8f3a", "parent_task": "t-8f00", "context_id": "ctx-a1",
  "capability": "contract-review",
  "objective": "审查 X 组织股权转让协议中的对赌条款风险",
  "output_spec": {"format": "markdown", "artifacts": ["review_report"]},
  "inputs": {"parameters": {…}, "artifacts": [{"name": "contracts", "uri": "s3://…"}]},
  "budget": {"tokens": 500000, "deadline": "…"},
  "constraints": ["不得访问外部网络", "引用需注明条款编号"] }

成员加入先跑 MiloPack 自带 evals（冒烟）才置 Ready——"试用期"语义，复用包内质检报告
  • 调和与调度分离：调和管"组织编制符合 org.yaml"；调度管"用户请求 → LLM 任务分解 → CEL 路由 → 派发 → 汇总交付"。

现实身份定位

秘书长（系统名 Secretariat，原 Conductor）≈ 办公室主任 / 幕僚长（Chief of Staff）：不是经理（无自主方向，权力全部来自用户授权且范围写在制度里）、不是成员（不干具体的活）。职责六项——听懂任务（唯一用 LLM）、派单、跟进汇总、挡驾与请示、人事执行（人事决定权只属于用户：招募/请离/版本变更一律用户发起，秘书长仅执行、可建议、禁止自动变动）、验收交付；除第一项外全部是照章执行的确定性代码，"制度长了手脚"，没有"主张"这个功能。

风险与 Spike 清单

风险评估对策
DeerFlow 迭代过快高合同只依赖公开端点；config_version 模板矩阵；MiloPack 只聚合官方概念
恶意包 / 供应链高三重审查 + 容器隔离 + 包签名 + 配置零代码
双边市场冷启动高单边价值先行（生成向导 + 编排自用成立）+ 自营种子
字节官方下场做市场中差异化押质检 + 实例间编排 + 企业私有化

Spike 验证项（优先级排序）

  1. escalate 事件形态：起一实例，构造需澄清任务，抓全 SSE 事件流——全案唯一未核实的合同环节
  2. enroll 全链路自动化：MiloPack → config.yaml 渲染 + /api/agents + skills 安装
  3. 进程内 / 容器双实现的行为一致性
  4. webhook 可靠性与 deliver 产物完整性校验
  5. CEL 引擎选型：cel-python 仅 Beta → conformance 测试集验收，或 Go sidecar
